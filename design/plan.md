# План: личная музыкальная библиотека из Spotify, YouTube Music и своих файлов

Статус: черновик на согласование · прототип интерфейса — [prototype.html](prototype.html)

## 1. Цель и рамки

**Зачем сервис.** Бэкап всего, что слушается в Spotify и YouTube Music, плюс ручные загрузки — так, чтобы
со временем можно было уйти с площадок. Музыку раздаёт Navidrome, слушаем в Arpeggi (iPhone, iPad).

**Входит:**

1. Новый интерфейс по прототипу (меню сбоку на десктопе, вкладки снизу на телефоне).
2. Индекс библиотеки: каждый файл знает свои источники.
3. Склейка дублей между площадками и внутри одной.
4. Синк YouTube Music: «Понравившиеся» и выбранные плейлисты.
5. Плейлист как одна сущность из нескольких источников (Spotify + YouTube Music).
6. Единый поиск: библиотека → YouTube Music, Deezer, Spotify; скачивание одной кнопкой.
7. Поиск площадок прямо в клиенте (прокси Subsonic перед Navidrome).

**Позже (записано, не делаем сейчас):** миксы YouTube Music («Супермикс», «Открытия»), подборки
ListenBrainz по прослушиваниям в Navidrome — раздел «Открытия».

**Не делаем:** свои приложения под iOS/Android/десктоп; удаление файлов без явного решения
пользователя; FLAC (нужен платный lossless-сервис).

## 2. Как устроено сейчас и что меняется

Сейчас всё держится на spotdl: `playlists.txt` → `spotdl sync <ссылка>` → spotdl сам решает, что
качать, пишет `*.spotdl` (save-файлы), `errors/*.txt` и m3u. Сервис только запускает его и читает
эти файлы. Так нельзя ни склеить дубли между площадками, ни собрать плейлист из двух источников:
spotdl знает только Spotify и только свой плейлист.

**Новая схема — сервис ведёт библиотеку сам, spotdl остаётся одним из загрузчиков:**

```
источники (списки треков)        индекс библиотеки (SQLite)        загрузчики (звук)
  Spotify: плейлист/альбом/  ──►  сопоставление: уже есть?   ──►  YouTube (spotdl / yt-dlp)
  Любимые                         да → ссылка на файл              Deezer по ISRC
  YouTube Music: плейлист/        нет → в очередь загрузки         Spotify напрямую (librespot)
  Понравившиеся                   сомнительно → «Внимание»         свой файл
  ручные загрузки / поиск                │
                                         ▼
                           m3u-плейлисты → Navidrome → Arpeggi
```

- **Источник** только отдаёт список треков с метаданными (название, исполнители, альбом,
  длительность, ISRC если есть, ID на площадке). Ничего не качает.
- **Индекс** решает, есть ли трек в библиотеке, и хранит связи «файл ↔ источники ↔ плейлисты».
- **Загрузчик** качает звук для того, чего нет, и кладёт файл через общий `place_file`.
- **m3u** генерируются из индекса, а не spotdl — поэтому в плейлист из двух источников попадают
  одни и те же файлы без повторов.

Что из нынешнего остаётся: очередь задач и две дорожки, локи, анти-бан librespot, апгрейд 320k,
Navidrome-скан, вход/пароль, настройки (реестр `FIELDS`), Deezer, загрузка файлов, проба YouTube,
паузы, фильтр лога. Liked Songs уже работают по новой схеме (свой список → `spotdl download`) —
это образец для остальных.

## 3. Индекс библиотеки

Файл `/conf/library.db` (SQLite из стандартной библиотеки Python, без сервера).

| Таблица | Что хранит |
|---|---|
| `tracks` | один ряд на запись: путь к файлу (или пусто — «не скачан»), название, исполнители, альбом, длительность, ISRC, битрейт/формат, когда добавлен |
| `track_ids` | внешние ID трека: `spotify:<id>`, `youtube:<videoId>`, `deezer:<id>`, `isrc:<код>` — по ним ищутся совпадения |
| `playlists` | плейлисты сервиса: имя, автосинк, порядок |
| `playlist_sources` | источники плейлиста: `spotify_playlist`, `spotify_album`, `spotify_liked`, `ytm_playlist`, `ytm_liked` + ссылка, время и итог последнего синка |
| `playlist_items` | состав плейлиста: трек, позиция, из какого источника пришёл |
| `match_candidates` | возможные дубли: два трека, процент, причина, решение пользователя |
| `missing` | почему трек не скачан и что уже пробовали (вместо `errors/*.txt`) |

**Откуда берётся индекс для уже скачанной библиотеки.** spotdl пишет в каждый mp3 ссылку на трек
Spotify (`WOAS`), ссылку на ролик YouTube, откуда взят звук (`COMM`), и ISRC (`TSRC`); то же пишет
наш `place_file` для Deezer/librespot/своих файлов. Поэтому первичный индекс собирается сканом
тегов `/music` — без единого запроса к площадкам. Сверху докладываются save-файлы (`*.spotdl`:
состав плейлистов), `errors/*.txt` (что не скачано) и `playlists.txt` (какие плейлисты есть).

**Раскладка файлов.** Шаблон для новых файлов остаётся `{album-artist}/{album}/{track-number} -
{title}`; для треков YouTube без альбома — `{artist}/Синглы/{title}`. Существующие файлы на
первом этапе не двигаем. Если позже захотим перенести: в текущем Navidrome ID трека строится по
тегам (MusicBrainz ID или альбом + диск + номер + название), а не по пути, так что звёзды и
прослушивания переживут перенос, если не менять теги. Проверить вашу версию Navidrome перед этим.

## 4. Склейка дублей

Дубль — **та же запись** с разных площадок или из разных плейлистов. Ремастер, live, кавер,
«Russian ver.», радио-версия — разные треки, если вы не решите иначе.

Уровни сопоставления, от точного к нечёткому:

| Уровень | Как | Решение |
|---|---|---|
| 1 | тот же `videoId` YouTube (spotdl уже брал звук для трека Spotify с этого ролика) | склеить сразу |
| 2 | тот же ISRC | склеить сразу |
| 3 | нормализованные исполнитель + название совпали, длительность ±3 с | склеить сразу |
| 4 | похоже, но не точно (название отличается, длительность ±3–10 с, другой исполнитель) | в «Внимание» с процентом |
| 5 | акустический отпечаток (Chromaprint) — для перезаливов и lyric video | позже, если уровней 1–4 не хватит |

Нормализация: регистр, `feat.`/`ft.`/`with`, скобки «Official Video / Audio / Lyrics / Remastered
20xx / HD», кавычки, транслитерация не трогается (кириллица и японский сравниваются как есть).
Маркеры версии (`live`, `remix`, `cover`, `acoustic`, `ver.`, `instrumental`, `slowed`) — НЕ
вырезаются: из-за них трек и считается другим.

При склейке остаётся файл лучшего качества; второй файл не удаляется, а уходит в «корзину»
сервиса (`/music/.trash`, очистка вручную), ссылки плейлистов переводятся на оставшийся.

## 5. Синк YouTube Music

- **Список:** библиотека `ytmusicapi` с теми же `cookies.txt` (заголовки собираются из cookies):
  «Понравившиеся» (`LM`), список ваших плейлистов (для выбора в настройках), состав плейлиста —
  `videoId`, название, исполнители, альбом, длительность, обложка.
- **Звук:** `yt-dlp` по `videoId` → `place_file` (mp3, теги, обложка). ISRC у YouTube Music часто
  нет — склейка опирается на уровни 1 и 3.
- **Ограничения:** звук с YouTube ниже по качеству (обычно 128–160k, Premium — до 256k); для треков,
  которые есть и в Spotify, после склейки можно прогнать апгрейд 320k. Те же паузы и проба блока,
  что у синка Spotify. Cookies общие — поэтому важна инструкция с приватным окном.

## 6. Поиск

- **В интерфейсе сервиса:** библиотека (полнотекстовый индекс SQLite FTS5) → YouTube Music
  (`ytmusicapi.search`), Deezer (открытое API поиска, без ключа), Spotify (осторожно: лимиты
  dev-приложения — только по явному запросу, с кэшем). Результаты склеиваются тем же сопоставлением:
  «есть в библиотеке», «лучший источник».
- **Скачать из поиска:** трек — по лучшему источнику (Deezer 320k → Spotify 320k → YouTube);
  альбом — только недостающие; результат попадает в библиотеку и, по выбору, в плейлист.
- **В Arpeggi (этап 6):** сервис отвечает по Subsonic API, всё проксирует в Navidrome, а в ответ
  на поиск (`search3`) добавляет результаты площадок; нажатие на такой трек ставит его в загрузку.
  Сначала проверяем, как Arpeggi показывает такие треки и что делает при воспроизведении
  несуществующего пока файла; если плохо — подбираем клиент. Перед тем как писать свой прокси,
  смотрим готовые решения.

## 8. Риски и открытые вопросы

- **Лимиты площадок.** Spotify штрафует dev-приложения на сутки (уже видели), YouTube режет
  анонимные сессии. Всё, что ходит на площадки, — с паузами, кэшем и памятью о штрафах.
- **Cookies YouTube** общие для синка, поиска и списков — протухли, ломается всё сразу. Проба и
  явное предупреждение на главной.
- **Ложные склейки** хуже пропущенных дублей: пороги консервативные, сомнительное — к вам, второй
  файл — в корзину, а не удаляется.
- **Переход со spotdl sync на свою оркестровку** (этап 3) — самое рискованное место: делаем рядом
  со старой схемой и сравниваем итоги, прежде чем переключить автосинк.
- **Память:** индекс и сканер — в отдельном процессе/задаче, веб остаётся лёгким; лимит 2 ГБ.
- **Arpeggi** может не поддержать то, что нужно для поиска в клиенте, — тогда другой клиент.
- **Вопрос:** версия Navidrome на сервере (для решения о переносе файлов) — проверим через
  «Проверить» в настройках Navidrome.

## 9. Как проверяем

- Юнит-тесты на нормализатор, сопоставление, импорт (на копиях реальных save-/errors-файлов).
- Локально — сервис на тестовой папке с несколькими сотнями файлов; на сервере — сначала только
  чтение (индекс и отчёт), потом запись.
- Перед этапами 3 и 4 — прогон `/code-review` (рискованные изменения на тысячах треков).
- Каждый этап — отдельные коммиты по вашему «закоммить», выкатка через Re-pull.
